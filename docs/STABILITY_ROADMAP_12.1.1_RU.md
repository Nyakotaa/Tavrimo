# Tavrimo 12.1.1 — план стабилизации и чек-лист проверки

## Цель

Довести существующий рабочий PWA-прототип до предсказуемого состояния, не меняя согласованную продуктовую концепцию и не добавляя новые пользовательские функции до закрытия критических рисков.

## Что изменено в локальной копии 12.1.1

1. Импорт JSON-резервной копии требует подтверждения до замены текущих задач, настроек, статистики и локального расписания.
2. Если LocalStorage не смог сохранить импорт, прежнее состояние возвращается в памяти приложения.
3. Sync Gateway ограничивает кэш расписаний 200 записями и таблицу лимитера 10 000 IP-записями.
4. Лимитер использует `req.ip` Express, а не вручную читаемый `X-Forwarded-For`. Настройка доверия к одному proxy-hop (`trust proxy = 1`) должна соответствовать фактической конфигурации Render.
5. CORS явно описан как публичный read-only API без cookie/credentials; используется `Access-Control-Allow-Origin: *`.
6. `/api/rea/health` отвечает за liveness, `/api/rea/ready` отдельно проверяет запуск Chromium и создание контекста.
7. Gateway обнаруживает отключённый Chromium и пытается восстановить соединение при следующем запросе.
8. Если портал не отдаёт экспорт «За всё время», Gateway отклоняет видимую неделю как неполный ответ; ранее сохранённый полный календарь не перезаписывается.
9. Старые QA-снимки 12.0.x перемещены в `tools/historical/`, чтобы не воспринимались как актуальные проверки 12.1.1.

## Текущий результат локальных проверок

Проверены синтаксис `app.js`, `sw.js` и `sync-service/server.mjs`; 9 актуальных тестов ручного планирования, обработки расписания, onboarding, резервных парсеров, логики синхронизации, защиты импорта, ограничений Gateway и релиза 12.1.1; контроль PWA-манифеста, DOM-ID, иконок и cache-busting. Все эти локальные проверки пройдены. Исторические тесты старых версий перенесены в `tools/historical/`.

Локальные проверки не доказывают работоспособность опубликованного Render-сервера или фактическое получение расписания от `rasp.rea.ru`. Из этого окружения DNS-запрос к `tavrimo-rea-sync.onrender.com` не разрешился, поэтому опубликованные `/health`, `/ready` и `/schedule` проверить не удалось. Сам портал `rasp.rea.ru` открылся для просмотра: на странице присутствуют поиск группы и выбор экспорта «За всё время», но динамический запрос группы из этой проверки не выполнялся.

## План следующих работ

| Этап | Работа | Проверка готовности | Приоритет |
|---|---|---|---|
| A | Проверить опубликованный Render Gateway: `/health`, `/ready`, ошибки и логи | Health жив; Chromium ready; повторный запрос после cold start проходит | P0 |
| B | Проверить поиск группы РЭУ | Тестовая группа находится стабильно; диагностика объясняет неудачу | P0 |
| C | Проверить полный диапазон расписания | Выгрузка содержит события нескольких прошлых и будущих недель; нет тихого возврата только одной недели | P0 |
| D | Проверить ручной импорт `.ics` | Корректно распознаются время, аудитории, преподаватели; невалидный файл не стирает старое расписание | P0 |
| E | Проверить жизненный цикл данных | Создание/редактирование/завершение/удаление, перезагрузка, offline, импорт/экспорт без потери данных | P0 |
| F | Проверить UI на реальных мобильных размерах | 320, 360, 390 px; длинные названия, пустые состояния, ошибки синхронизации, модальные окна | P1 |
| G | Исправить доступность модальных окон | Клавиатурный фокус удерживается внутри; Escape закрывает окно, если действие безопасно; фокус возвращается инициатору | P1 |
| H | Собрать smoke/regression suite и релизный чек-лист | Все актуальные проверки исполняются одним CI job без исторических тестов | P1 |

## Ручной сценарий проверки синхронизации

1. Открыть опубликованный `/api/rea/health`; записать JSON и HTTP-код.
2. Открыть `/api/rea/ready`; дождаться `ready: true`.
3. Запросить расписание тестовой группы обычным запросом.
4. Повторить запрос с `If-None-Match` из первого ответа; при неизменном расписании допустим `304`.
5. Повторить с `force=1`; сравнить состав событий и отметку времени.
6. Сравнить минимум две даты в прошлом и две даты в будущем с `rasp.rea.ru`.
7. Временно имитировать недоступность upstream только в тестовом окружении; убедиться, что ранее сохранённое расписание остаётся доступным офлайн, а UI явно показывает ошибку обновления.

## Критерий стабилизации до новых функций

- Ни один пользовательский сценарий не приводит к незаметной потере задач или расписания.
- Полный календарь подтверждён реальным экспортом; недельный fallback не принимается за полный календарь и не перезаписывает сохранённые данные.
- Render liveness и Chromium readiness проверяются отдельно.
- Все текущие регрессионные тесты проходят в CI.
- Результат проверен как минимум на одном реальном iPhone/Safari и одном мобильном браузере Android/Chrome либо в эквивалентных браузерных окружениях с документированными ограничениями.

## Ограничения

Пока не получены реальные логи Render, ответ опубликованного Gateway и свежий экспорт `.ics`, нельзя заявлять, что синхронизация РЭУ исправлена. Для публикации изменений backend требуется отдельный deploy; ZIP сам по себе Render не обновляет.
